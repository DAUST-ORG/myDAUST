# Phase 0 · release-please + Conventional Commits

## Why

`CHANGELOG.md` is abandoned (last genuine entry 2026-06-28, current entry
describes features that no longer exist). The three deployable apps
(`apps/api`, `apps/portal`, `apps/vitrine`) release independently and the
promotion flow (`develop` → `main`) gives no signal of what changed. Without a
changelog generator the burden falls on every PR author to remember.

release-please is the boring choice for this: it derives the next version from
Conventional Commit history, opens a release PR, and regenerates a fresh
`CHANGELOG.md` on merge. AGENTS.md §16 already mandates Conventional Commits
with a scope, so this branch adds the tooling rather than the convention.

## Scope

### release-please config

`release-please-config.json` at repo root:

```json
{
  "packages": {
    "apps/api":    { "releaseType": "node", "packageName": "@mydaust/api" },
    "apps/portal": { "releaseType": "node", "packageName": "@mydaust/portal" },
    "apps/vitrine":{ "releaseType": "node", "packageName": "@mydaust/vitrine" }
  },
  "pull-request-header-pattern": "^release:\\s*",
  "group-pull-request-patterns": [
    { "group": "API",    "patterns": ["feat(api):", "fix(api):", "refactor(api):"] },
    { "group": "Portal", "patterns": ["feat(portal):", "fix(portal):", "refactor(portal):"] },
    { "group": "Vitrine","patterns": ["feat(vitrine):","fix(vitrine):","refactor(vitrine):"] }
  ],
  "changelog-path": "CHANGELOG.md",
  "versioning": "default",
  "branches": [{ "branch": "main" }]
}
```

`.release-please-manifest.json` at repo root, with the current versions read
from each package's `package.json` and `0.1.0` as the floor for any package
without one.

`.github/workflows/release-please.yml`:

- Triggers on push to `main` and on the `release:` PR label.
- Runs `googleapis/release-please-action@v4` with the manifest + config above.
- OIDC for npm publish is intentionally NOT configured — none of the three
  packages publish to npm today and AGENTS.md §2 confirms they're consumed
  through workspaces. The `releaseType: node` is so release-please knows the
  shape, not for npm.

### Conventional Commits scope check

`scripts/check-commit-msg.mjs` at repo root, runnable as
`pnpm commit:check "<msg>"`:

- Splits the subject line on the first `(`, expecting `type(scope): subject`.
  `type` ∈ `feat|fix|chore|docs|refactor|test|perf|style|build|ci|release`.
- Accepts the existing `release:` prefix documented in AGENTS.md §16 by
  matching it before the parser runs.
- Accepts the existing `(AI-generated)` suffix per AGENTS.md §16 by stripping
  it before validation.
- Exits non-zero with the offending line and a one-sentence hint on failure.

Wire it into a thin pre-push hook via `.husky/pre-commit`? **No.** Per
AGENTS.md §17 ("Still unbuilt and safe to assume absent"), agent-initiated
tooling should be opt-in. The script is committed and documented in
`CONTRIBUTING.md` (new file) and called explicitly: `pnpm commit:check
"feat(api): ..."`.

### CHANGELOG policy

Delete the existing `CHANGELOG.md` content and replace with:

```md
# Changelog

This file is generated by [release-please](https://github.com/googleapis/release-please)
from Conventional Commits. Do not edit by hand.

<!-- release-please-start -->
<!-- release-please-end -->
```

Per the user's decision, no backfill of the 2026-06-28 → today window. The next
release-please PR writes the first regenerated entry on its first run.

## Acceptance criteria

1. `release-please-config.json` and `.release-please-manifest.json` validate
   against the release-please v4 JSON schema (verified by a
   `release-please validate-config` dry run in CI).
2. A test branch with three squash-merged commits
   (`feat(api): …`, `fix(portal): …`, `chore(deps): …`) produces a release-please
   PR whose body lists those three commits under separate group headings and
   proposes semver bumps consistent with Conventional Commits (`feat` →
   minor, `fix` → patch, `chore` → none).
3. The `pnpm commit:check` script:
   - Accepts `feat(api): add foo` and `feat(api): add foo (AI-generated)`.
   - Accepts `release: api v0.2.0`.
   - Rejects `updated stuff` with a clear message.
   - Rejects `feat(api)missing space` with a clear message.
4. `CHANGELOG.md` is committed with the marker comment block. The previous
   content is deleted; `git log --follow CHANGELOG.md` shows the rewrite.
5. `CONTRIBUTING.md` exists at the repo root with the four required sections.
6. `pnpm -r typecheck` still passes (no source changes).

## Out of scope

- Auto-merge of release PRs. Senior review still required (matches the user's
  workflow for Phase 0 PRs).
- Slack / email notifications on release PRs.
- Renaming any of the three packages or changing their public APIs.
- npm publish pipeline (no package publishes today).

## Risks

- **AGENTS.md §16 says "agent-authored work carries the literal suffix
  `(AI-generated)` in the subject line."** The commit-msg checker strips this
  suffix before validation, so the existing convention keeps working.
- **AGENTS.md §16 also says "release: prefix"** is used for `develop`→`main`
  promotions. release-please's `pull-request-header-pattern` is set to
  `^release:\s*` so release-please PRs merge cleanly without being re-parsed
  as Conventional Commits.
- **First-run noise**: the first release-please PR will propose a version bump
  for any package whose existing `package.json` doesn't match release-please's
  inferred version. The manifest floors it at the current `package.json`
  version, so this is one PR and then steady state.
- **Existing PRs in flight** (if any) will have non-conforming subjects. This
  branch does not retroactively lint them; it makes the rule live going forward.
