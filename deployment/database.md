# Database

The most consequential part of this system: `daust-prod-pg` holds ~298 real students,
~1.28 billion XOF of invoices, and thousands of transcript entries. Nothing in this document
should be run against it without reading the guard it trips.

Verified against the repository on 2026-08-24. Not verified against live AWS — see
[`README.md` §1](README.md#unverified-not-confirmed-against-live-aws).

---

## 1. The instance

PostgreSQL on RDS, defined in `infra/modules/rds/main.tf` and parameterised from
`infra/environments/prod/main.tf`.

| Property | Production | Source |
| --- | --- | --- |
| Identifier | `daust-prod-pg` | `modules/rds/main.tf:13` (`daust-${var.env}-pg`) |
| Engine | `postgres`, version `"16"` | `modules/rds/variables.tf` default |
| Instance class | `db.t4g.small` | `environments/prod/main.tf` |
| Storage | 20 GB `gp3`, `storage_encrypted = true` | `modules/rds/main.tf` |
| Database name | `mydaust` | `modules/rds/variables.tf` default |
| Master user | `mydaust` | `modules/rds/variables.tf` default |
| Master password | `random_password.db` (32 chars, no specials), generated by terraform | `environments/prod/main.tf` |
| Backups | `backup_retention_period = 7` days | `modules/rds/main.tf:31` |
| Deletion protection | `true` | `environments/prod/main.tf` |
| Final snapshot | `skip_final_snapshot = false` | `environments/prod/main.tf` |
| Publicly accessible | **`true`** | `environments/prod/main.tf` |
| `apply_immediately` | `true` — parameter changes take effect at once, no maintenance window | `modules/rds/main.tf` |
| Subnet group | `daust-prod`, spanning two subnets in `us-east-1a`/`us-east-1b` | `modules/network/main.tf` |

`publicly_accessible = true` plus DB subnets attached to the IGW route table means the instance is
reachable from the internet. The only thing in front of it is security group `daust-prod-db`,
which allows 5432 from the ECS task SG and from `var.admin_cidr` — a value the terraform validates
to be a single `/32`. This exists so migrations can run from an operator's laptop. It is the
sharpest edge in the whole stack; see
[`infrastructure.md`](infrastructure.md#network--inframodulesnetwork).

Nothing in this repo enables Multi-AZ, a read replica, Performance Insights, or a custom
parameter group. **UNVERIFIED:** whether any of those were enabled by hand outside terraform —
check with `aws rds describe-db-instances --db-instance-identifier daust-prod-pg`.

## 2. How `DATABASE_URL` reaches the API

Four hops. No `.env` file is involved in production.

1. **Composed in terraform.** `infra/environments/prod/main.tf`:
   ```hcl
   database_url = "postgresql://mydaust:${random_password.db.result}@${module.rds.address}:5432/mydaust?schema=public"
   ```
2. **Written to Secrets Manager.** `module "secrets"` receives it in its `secrets` map;
   `infra/modules/secrets/main.tf` creates one `aws_secretsmanager_secret` per key named
   `daust-<env>/<KEY>`. The production parameter path is:

   ```
   daust-prod/DATABASE_URL
   ```

   (also `daust-prod/SESSION_SECRET`, and conditionally `daust-prod/RESEND_API_KEY` and
   `daust-prod/TUNNEL_CREDS`.) These are **Secrets Manager secrets, not SSM parameters** — there
   is nothing in SSM Parameter Store. Every secret carries
   `recovery_window_in_days = 0`, so deletion is immediate and unrecoverable.

3. **Injected into the container.** `infra/environments/prod/main.tf` passes
   `secrets = [{ name = "DATABASE_URL", valueFrom = module.secrets.arns["DATABASE_URL"] }, ...]`
   into `modules/ecs-service`, which renders them as the task definition's `secrets` array. ECS
   resolves them at task start using the **execution** role, which carries an inline
   `secretsmanager:GetSecretValue` policy scoped to exactly those ARNs
   (`modules/ecs-service/main.tf`, `aws_iam_role_policy.execution_secrets`).

4. **Read at boot.** `apps/api/src/config/env.ts` validates `DATABASE_URL: z.string().url()` —
   required, no default. A missing or malformed value throws
   `Invalid environment:\n  - DATABASE_URL: ...` before Nest starts, so the task exits and the
   ALB never marks it healthy.

**Retrieving the value** (only when you genuinely need it — for a manual migration or a psql
session):

```sh
aws secretsmanager get-secret-value --secret-id daust-prod/DATABASE_URL \
  --query SecretString --output text
```

or from terraform:

```sh
cd infra/environments/prod
tofu output rds_address
tofu output -raw db_password
```

Never paste the result anywhere. It is the whole database.

## 3. Migrations

**60 migration directories** under `packages/db/prisma/migrations/`, plus `migration_lock.toml`
(`provider = "postgresql"`). Confirmed identical at the deployed SHA:
`git ls-tree -d --name-only 9d1f14c packages/db/prisma/migrations/ | wc -l` -> 60.

Migrations after 2026-07-23 are **hand-authored SQL** in hand-named directories with rounded
timestamps (e.g. `20260821140000_person_lifecycle`). They carry PostgreSQL that `schema.prisma`
cannot express: 21 named CHECK constraints, partial unique indexes, one functional unique index
(`Student_studentNo_lower_key`). Enum-value additions are deliberately isolated into their own
migration because PostgreSQL requires the `ADD VALUE` to commit first.

**Never edit an applied migration.** There are no `down` migrations — the schema is forward-only.

### How they run on deploy

`.github/workflows/deploy.yml`, step *Run migrations (one-off ECS task on the freshly built
image)*, which is step 1 of the `app` job and runs **before** the API rolls:

1. Read the service's current task definition ARN and `networkConfiguration` from
   `ecs describe-services`.
2. `ecs describe-task-definition`, strip the read-only fields with `jq`, and **replace
   `containerDefinitions[0].image` with the freshly built `daust-api:<tag>`**. This is the whole
   point: running the current task def would execute the *old* image's migration folder, silently
   skip the new migrations, and the newly rolled API would then 500 on columns that do not exist.
3. `ecs register-task-definition` -> `$MIGTD`.
4. `ecs run-task --launch-type FARGATE` with a container override:
   ```
   node node_modules/prisma/build/index.js migrate deploy \
     --schema=node_modules/@mydaust/db/prisma/schema.prisma
   ```
   reusing the service's `networkConfiguration` so the task lands in the VPC and passes the
   `daust-prod-db` security group.
5. `ecs wait tasks-stopped`, read `containers[0].exitCode`, and `[ "$EXIT" = "0" ]` — a non-zero
   exit fails the deploy before anything rolls.

`$MIGTD` and `$NET` are exported to `$GITHUB_ENV` and reused by the next step,
`load-sis-reference.ts`, which must run on the same new-image task def for the same reason.

In run 32514030565 that migration task definition was `daust-prod-api:138`, and the API service
subsequently rolled to `daust-prod-api:139`.

### Running migrations manually

Two ways. Prefer the ECS one — it needs no database credentials on your machine and no SG change.

**A. As a one-off ECS task** (the same thing CI does):

```sh
CLUSTER=daust-prod
SERVICE=daust-prod-api
TD=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
      --query 'services[0].taskDefinition' --output text)
NET=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
      --query 'services[0].networkConfiguration' --output json)

TASK=$(aws ecs run-task --cluster "$CLUSTER" --task-definition "$TD" \
  --launch-type FARGATE --network-configuration "$NET" \
  --overrides '{"containerOverrides":[{"name":"api","command":["node","node_modules/prisma/build/index.js","migrate","deploy","--schema=node_modules/@mydaust/db/prisma/schema.prisma"]}]}' \
  --query 'tasks[0].taskArn' --output text)

aws ecs wait tasks-stopped --cluster "$CLUSTER" --tasks "$TASK"
aws ecs describe-tasks --cluster "$CLUSTER" --tasks "$TASK" \
  --query 'tasks[0].containers[0].exitCode'
aws logs tail /ecs/daust-prod-api --since 10m
```

This runs the migration folder baked into **whatever image the service is currently on**. If you
need a newer migration set, register a task definition carrying the newer image first, exactly as
deploy.yml does.

**B. From a laptop.** Requires your public IP to be `var.admin_cidr` (re-apply terraform if it
changed) and the real `DATABASE_URL`:

```sh
export DATABASE_URL="postgresql://mydaust:<password>@<rds_address>:5432/mydaust?schema=public"
pnpm --filter @mydaust/db exec prisma migrate deploy
```

Note there is no `.env` in `packages/db` — Prisma reads only the exported variable or the repo
root `.env` (AGENTS.md §1).

**Do not use `prisma migrate dev` or `prisma migrate reset` against anything but a local
database.** `migrate dev` will offer to reset the schema.

### Writing a new migration

Author it locally against Docker Postgres (`docker compose up -d`), then commit the generated SQL.
Because the SQL is hand-maintained after 2026-07-23, review the emitted file rather than trusting
it. Reason about it against live data before merging: merging to `main` runs it against production
with no approval gate.

## 4. Bootstrapping a brand-new database

Three scripts under `packages/db/prisma/`, mutually exclusive, each with its own guard. This table
is the one thing to get right.

| Script | npm script | Target | Guard |
| --- | --- | --- | --- |
| `seed.ts` | `pnpm --filter @mydaust/db run seed` | local / staging demo data | exits 1 if `DATABASE_URL` contains `daust-prod`, unless `SEED_ALLOW_PROD=1` (`seed.ts:10`) |
| `bootstrap-prod.ts` | `bootstrap:prod` | real production, **first run only** | throws unless `student.count() === 0` **and** `payment.count() === 0` |
| `prod-accounts.ts` | `accounts:prod` | production staff logins, any time | throws if no `*_PASSWORD` env var is set; each password must be >= 12 chars |
| `load-sis-reference.ts` | `load:sis-reference` | any populated DB; runs on **every** deploy | asserts student/invoice/payment counts are unchanged and throws if any moved |
| `normalize-staging-legacy-demo.ts` | `normalize:staging-demo` | staging only | throws unless `TARGET_ENV=staging` |

### Order for a new production database

```sh
# 1. schema
DATABASE_URL=... pnpm --filter @mydaust/db exec prisma migrate deploy

# 2. reference data + the first admin
DATABASE_URL=... pnpm --filter @mydaust/db run bootstrap:prod

# 3. the rest of the staff logins, passwords supplied by you
ADMIN_PASSWORD=... REGISTRAR_PASSWORD=... BURSAR_PASSWORD=... \
HR_PASSWORD=... IT_PASSWORD=... COMMS_PASSWORD=... FACULTY_PASSWORD=... \
DATABASE_URL=... pnpm --filter @mydaust/db run accounts:prod
```

Students, parents and faculty are provisioned from the admin dashboard, not from these scripts —
`prod-accounts.ts` prints exactly that reminder.

### `bootstrap-prod.ts`

*"Minimal PRODUCTION bootstrap: reference data + one admin. No demo students, no fake money."*

Environment: **`DATABASE_URL` only.**

Guard, in `main()`:

```ts
const students = await prisma.student.count();
const payments = await prisma.payment.count();
if (students > 0 || payments > 0) {
  throw new Error(`Refusing to bootstrap: database is not empty (${students} students, ${payments} payments). ...`);
}
```

It then writes, in order:

1. `costCenters()` — upserts every entry of `COST_CENTERS` from `@mydaust/shared`, parents first.
2. `moneyConfig()` — five `FeeItem` rows (tuition, housing, cafeteria, application_fee, insurance)
   from `FEE_STRUCTURE`, and `SCHOLARSHIP_TIERS` if the table is empty.
3. `academicCatalog()` — term `Fall 2026`, department `CE`, programs `BSCE` / `BSEE` / `BSME`.
4. `seedSisReference(prisma)` — grading scales, catalogue years, degree requirements, fee
   schedule. Note this **throws on deploy** if any approved engineering curriculum does not total
   exactly 300 credits (AGENTS.md §7).
5. `adminAccount()` — upserts `admin@daust.edu` with roles `["admin","bursar"]` and a
   `randomBytes(18).toString("base64url")` password hashed with bcrypt cost 12.

**The generated admin password is printed to stdout once and stored nowhere.** Capture it from
the terminal (or, if run as an ECS task, from `/ecs/daust-prod-api` in CloudWatch — which means it
lands in a 30-day log group; prefer `prod-accounts.ts` immediately afterwards to replace it with a
password you chose).

### `prod-accounts.ts`

*"Operator tool: create/reset PROD staff logins with passwords YOU supply via env. Passwords
never live in this file or in git."*

Idempotent upsert; touches only the seven listed staff accounts and never student, payment or
invoice data.

| Email | Roles | Password env var |
| --- | --- | --- |
| `admin@daust.edu` | `admin`, `bursar` | `ADMIN_PASSWORD` |
| `registrar@daust.edu` | `registrar`, `admin` | `REGISTRAR_PASSWORD` |
| `bursar@daust.edu` | `bursar` | `BURSAR_PASSWORD` |
| `hr@daust.edu` | `hr` | `HR_PASSWORD` |
| `it@daust.edu` | `it_admin` | `IT_PASSWORD` |
| `comms@daust.edu` | `communications` | `COMMS_PASSWORD` |
| `faculty@daust.edu` | `faculty` | `FACULTY_PASSWORD` |

**Mechanism.** Each account is selected only if its env var is present and non-empty
(`ACCOUNTS.filter((a) => (process.env[a.env] ?? "").length > 0)`); omitting a variable skips that
account entirely. If none are set the script throws rather than doing nothing silently. Each
password is rejected below 12 characters, then hashed with `bcrypt.hash(pw, 12)`. The script logs
only the email and roles — *"Emails only — never log the password."*

The upsert's `update` branch also clears a suspension and bumps `sessionVersion`:

```ts
update: { roles, passwordHash, status: "active", suspendedAt: null, suspendedById: null,
          sessionVersion: { increment: 1 } }
```

Both halves are load-bearing. A DB CHECK constraint rejects setting `status` back to `active`
without clearing `suspendedAt` in the same statement, and the `sessionVersion` bump is what stops
a hostile session from outliving the reset. This is the **break-glass path** — do not "simplify"
it.

**Running it in production** (the file's own header): as a one-off ECS task on the api image,
same pattern as the deploy's migrate step, with the passwords set as a container override. That
puts the passwords into the `run-task` API call. Prefer generating them locally with a password
manager, and rotate immediately if anything about the invocation was captured.

Do not put a real password in a shell history, a workflow input, a PR, or this repository.

### `load-sis-reference.ts`

Runs on **every deploy**, step 2 of the `app` job. Loads only official configuration into an
already-bootstrapped database, because `bootstrap-prod.ts` refuses to run once students exist and
an environment bootstrapped before the SIS redesign would otherwise have empty grading,
degree-audit and fee screens.

Its safety property is an assertion, not a promise: it counts students / invoices / payments
before and after and throws if any count moved. That assertion failing fails the deploy.

Caveat from AGENTS.md §11: it is idempotent **except** that it hard-deletes and recreates every
`GradeScaleRow` and deletes `ProgramRequirement` rows outside its own list.

Environment: `DATABASE_URL` only.

### Local development database

```sh
docker compose up -d     # postgres:16-alpine on :5432, user/pass/db all "mydaust"
export DATABASE_URL="postgresql://mydaust:mydaust@localhost:5432/mydaust?schema=public"
pnpm --filter @mydaust/db exec prisma migrate dev
pnpm --filter @mydaust/db run seed          # dev password for every seeded user: daust-dev-2026
```

`docker-compose.yml` persists to the named volume `mydaust_pgdata`.

## 5. Backup and restore

### What exists

- **Automated RDS backups, 7-day retention** (`backup_retention_period = 7`,
  `infra/modules/rds/main.tf:31`). That gives point-in-time recovery within a 7-day window via
  `aws rds restore-db-instance-to-point-in-time`.
- **A final snapshot on deletion** (`skip_final_snapshot = false` in prod) plus
  `deletion_protection = true`.
- **Encrypted storage** (`storage_encrypted = true`), so snapshots inherit encryption.
- **Manual snapshots, taken by hand before risky operations.** The precedent is in
  `docs/production-status.md`: the 2026-08-12 full-package conversion used snapshot
  `daust-prod-pre-full-package-conversion-20260812-114302`. `full-package-conversion.yml`
  enforces this for prod runs — it validates that `backup_reference` names a snapshot which is a
  manual, available, encrypted snapshot of `daust-prod-pg` before it will proceed.

### What does not exist

There is **no backup script, no restore runbook, no `pg_dump` anywhere, and no logical-export
job** in this repository. `grep -rniE "pg_dump|restore-db|create-db-snapshot"` over `docs/`,
`infra/`, `.github/` and `packages/db/` returns nothing. The only recovery mechanism is RDS's own.

`myDAUST Architecture and Build Plan.md:213` calls backups "non-negotiable" and asks for
"automated daily backups + point-in-time recovery" — RDS's 7-day retention satisfies the letter of
that, but there is no tested restore, no off-account copy, and no retention beyond a week.

**UNVERIFIED:** whether an AWS Backup plan, a cross-region snapshot copy, or a longer retention
was configured outside terraform. Check with:

```sh
aws rds describe-db-instances --db-instance-identifier daust-prod-pg \
  --query 'DBInstances[0].{retention:BackupRetentionPeriod,window:PreferredBackupWindow,multiaz:MultiAZ}'
aws rds describe-db-snapshots --db-instance-identifier daust-prod-pg --snapshot-type manual \
  --query 'DBSnapshots[].{id:DBSnapshotIdentifier,created:SnapshotCreateTime,status:Status}'
aws backup list-backup-plans
```

### Taking a manual snapshot before a risky operation

```sh
aws rds create-db-snapshot \
  --db-instance-identifier daust-prod-pg \
  --db-snapshot-identifier daust-prod-pre-<operation>-$(date -u +%Y%m%d-%H%M%S)
aws rds wait db-snapshot-available --db-snapshot-identifier <that id>
```

Do this before any migration that drops or rewrites data, before any importer run with
`CONFIRM=1`, and before any `full-package-conversion` prod run (where the workflow will refuse to
start without one).

### Restoring

RDS restores create a **new instance**; they never overwrite in place. So a restore is followed by
a cutover, which for this stack means updating `daust-prod/DATABASE_URL` in Secrets Manager and
rolling `daust-prod-api`. Sketch:

```sh
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier daust-prod-pg \
  --target-db-instance-identifier daust-prod-pg-restore-<date> \
  --restore-time <ISO8601 within the 7-day window> \
  --db-subnet-group-name daust-prod \
  --vpc-security-group-ids <daust-prod-db sg id>
```

Then verify the restored data, update the secret, and roll the service. **This procedure has never
been rehearsed as far as this repository records.** Rehearse it against staging before you need
it.

## 6. Schema facts worth knowing before you touch it

From AGENTS.md §11, which was verified against the code on 2026-08-18:

- `String @id @default(uuid())` for 100 of 106 models. Six natural keys: `CostCenter.code`,
  `ManagementCategory.key`, `AppSetting.key`, `FeeItem.key`,
  `StudentNumberSequence.academicYearStart`, `GuardianProfile.guardianId`.
- **No soft-delete columns.** Deletion is modelled per domain as `recordStatus`, `voidedAt`,
  `clearedAt`, or an invoice `void` status.
- Academic-year labels use a **U+2013 en dash** (`2026–2027`), and that label — not an id — is the
  foreign key from `FeeSchedule.academicYearLabel` to `AcademicYear.label`.
- `PaymentSubmission` is stored in a table still named `WireTransferSubmission` (`@@map`), its
  status enum is `WireTransferStatus`, and the DB spelling is `approved` while the wire contract
  says `verified`.
- `Student_studentNo_lower_key` is a functional unique index created via raw SQL. It is invisible
  to schema diffing, so Prisma will not warn you about it.
- Retired-portal tables are still present and dropping them is irreversible; **`MealPlan`,
  `DiningScan`, `Hall` and `HousingAssignment` must be kept** — live student screens read them.
